# Domo

A [Café Labs](https://cafelabs.net) product.

Household management app for families and groups — Android and Web.

## Features

- **Authentication** — email/password and Google Sign-In
- **Household** — create a household, join via a 6-character code, manage members (approve, reject, remove, set role), leave or delete the household; any active member can reorder the pantry categories for the household (`/casa/categorias`)
- **Pantry** — items registered by category with 3 statuses: *Have*, *Out*, *In cart*; optionally, per item, quantity + minimum stock tracking (status is then computed automatically from those numbers instead of being toggled manually)
- **Shopping List** — filtered view of the pantry; mark items as in cart and batch-update the pantry
- **Profile** — Google photo, household role, theme toggle (System / Light / Dark), language selector (System / Português / English), logout

## Configuration

Domo talks to a single Firebase project (`domo-8b336`, Spark/free plan) for
both Auth and Firestore. Unlike most stacks, the Firebase client config here
is **not a secret** — it only identifies the project to the client SDK; all
real access control is enforced server-side by `firestore.rules` (see
`docs/BACKEND.md`) — so these files are committed to this repo instead of
gitignored:

| File | Purpose | Where it comes from |
|---|---|---|
| `lib/firebase_options.dart` | Firebase client config (all platforms), generated by the FlutterFire CLI | `flutterfire configure`, run once against the `domo-8b336` Firebase project |
| `android/app/google-services.json` | Android-specific Firebase config | Firebase console → Project settings → Android app, or regenerated by `flutterfire configure` |
| `.firebaserc` | Points the `firebase` CLI at the `domo-8b336` project by default | committed, one line |
| `firebase.json` | Firestore rules/indexes paths, emulator ports, Hosting config | committed |

To point this codebase at a **different** Firebase project (e.g. your own for
local experimentation), re-run `flutterfire configure` — it rewrites
`firebase_options.dart` and `google-services.json` for the project you select.

One genuine secret exists, but only for an optional one-off script, never for
running the app itself: `scripts/backfill/backfill-codigos.mjs` (see
`scripts/backfill/README.md`) reads a service-account key **path** from the
`GOOGLE_APPLICATION_CREDENTIALS` environment variable. The key file itself
must never be committed (`.gitignore` blocks `*serviceAccount*.json` and
similar patterns) — obtain it from Firebase console → Project settings →
Service accounts → Generate new private key, and keep it outside the repo.

## Running the test suite

Two independent test suites, neither depending on the other:

**Flutter unit/widget tests** (`test/`, excluding `test/rules/`) — mock
Firestore/Auth via `fake_cloud_firestore` + `mocktail`, no emulator or network
needed:

```bash
flutter test
```

**Firestore security-rules tests** (`test/rules/`) — a standalone Node
harness with its own `package.json` (not part of `pubspec.yaml`'s dependency
tree) that runs only against the **local Firestore emulator**, never
production:

```bash
cd test/rules
npm install        # once

cd ../..            # back to the repo root
firebase emulators:exec --only firestore --project domo-rules-test \
  "node --test test/rules/rules.test.mjs"
```

Requires the `firebase` CLI on `PATH`. Locally, the `node` that
`firebase emulators:exec` injects into its subshell is firebase-tools' own
bundled `pkg` binary, which does not support the `--test` flag — if the
command above fails on that, invoke a real Node 20+ by its absolute path
instead of relying on `PATH` inside the subshell (see `docs/BACKEND.md`,
"Testing", and `docs/DEPLOY.md`'s CI section, which sidesteps the same quirk
in CI by using the Node that `actions/setup-node` puts on `PATH`).

## Architecture

**Feature-first + Clean Architecture** — each feature under `lib/features/` has
its own `data` / `domain` / `presentation` layers; state via Riverpod
(code-gen), navigation via `go_router`.

```
lib/
├── core/          # analytics, constants, providers (theme), router, theme
├── features/      # auth, casa (household), dispensa (pantry), mercado (shopping), profile
└── shared/        # widgets shared across features (HomeShell, DomoErrorState...)
```

Deeper dive (layers, provider patterns, routing, technical decisions):
**`docs/ARQUITETURA.md`**.
